# mini-games

Kyoto Dev Circle ミニゲーム集（Phase 1）

Phase 0 では Git と GitHub を使ったチーム開発の流れ（Issue → ブランチ → PR → レビュー → マージ）を身につけました。
Phase 1 では、その流れの上で、実際の開発現場で使われている技術を一つずつ取り入れながら、ミニゲーム集の Web サイトを作ります。

- 公開URL（完成後）：https://kyoto-dev-circle.github.io/mini-games/
- メンバー：はやと（standwind8810）、かもむつ（kamomutsu09-spec）
- 期間の目安：2026年11月9日〜2027年1月中旬（8スプリント、1スプリント＝1週間）
- やること：[Issues](https://github.com/kyoto-dev-circle/mini-games/issues)（#1〜#23）、[マイルストーン](https://github.com/kyoto-dev-circle/mini-games/milestones)
- 進み具合：[Kyoto Dev Circle タスクボード](https://github.com/orgs/kyoto-dev-circle/projects/1)

Git と GitHub の基本的な使い方は、[self-intro の Git/GitHub はじめてガイド](https://github.com/kyoto-dev-circle/self-intro/blob/main/docs/git-guide.md) を見てください。

## 1. 目標

1. 現場の開発基盤（npm、ビルドツール、自動チェック、自動テスト、自動公開）を自分たちで作り、その上で開発する
2. JavaScript の基礎（モジュール、DOM操作、イベント、状態管理、非同期処理）を、ゲームを作りながら身につける
3. ロジックと画面を分け、ロジックにはテストを書く習慣をつける
4. 外部サービス（Supabase）のデータベースとつながる機能を、安全に作る

## 4. フォルダ構成（予定）

```
mini-games/
├─ index.html              メニュー画面
├─ src/
│  ├─ main.js              メニュー画面の処理
│  ├─ style.css            共通のデザイン
│  └─ lib/                 ゲーム間で共通の部品（#14, #16, #20 で作る）
├─ games/
│  ├─ janken/
│  │  ├─ index.html        ゲームの画面
│  │  ├─ main.js           画面の処理（DOM操作・イベント）
│  │  ├─ logic.js          ゲームのルール（画面に触らない純粋な関数）
│  │  └─ logic.test.js     logic.js のテスト
│  ├─ number-guess/        同じ構成
│  └─ typing/              同じ構成
├─ docs/                   仕様書・設計（#15, #18, #23 で書く）
├─ supabase/               データベースの設定のSQL（#18, #19）
├─ .github/
│  ├─ workflows/           GitHub Actions の設定（#4, #5）
│  └─ pull_request_template.md
├─ vite.config.js
└─ package.json
```

一番大事な決まりは、**logic.js には画面の処理（document や window）を書かない**ことです。
ルールの部分を画面から切り離しておくと、テストが書きやすくなり、後で画面を作り直しても（React にするときなど）ロジックをそのまま使えます。

## 6. 開発ルール

Phase 0（self-intro）のルールをそのまま引き継ぎます。追加・変更点は太字の部分です。

- 作業は必ず Issue から始め、`feature/#Issue番号-内容` のブランチを作って PR を出す（**バグ修正は `fix/#番号-内容`**）
- コミットメッセージは `feat:`、`fix:`、`docs:`、`style:`、**`test:`（テストの追加・修正）、`ci:`（GitHub Actions の変更）、`refactor:`（動きを変えない整理）、`chore:`（設定や依存パッケージの変更）**で始める
- PR を出すときは Reviewers に相方を設定する
- マージには、もう1人の Approve が必要。マージは PR を出した本人が「Merge pull request」で行う（はやとのバイパスは Phase 0 と同じ）
- **CI（lint・フォーマット確認・テスト・ビルド）がすべて成功しないとマージできない**（#4 で設定）
- **ロジックを追加・変更したら、同じ PR でテストも追加・変更する**
- **レビューでは、Approve だけで終わらせず、良い点か改善点のコメントを最低1つ書く**
- **PR を出す前に、手元で `npm run lint`、`npm run format:check`、`npm test` を実行しておく**
- PR 本文に `Closes #番号` を書く。1つの Issue を2人の PR で進めるときは、最後にマージする PR だけ `Closes #番号`、ほかは `Refs #番号`
- 進み具合はタスクボードで管理する。作業を始めたらカードを手で In progress に動かす。In review と Done は自動で動くので、手で Done に動かさない
- **毎日 Slack に一言報告する（やったこと／次やること／困っていること）**。質問はスレッドで返す
- **Supabase のキーやパスワードは Issue・PR・Slack のチャンネルに貼らない。`.env.local` はコミットしない**

## 8. かもむつ向け：JavaScript の事前学習

#8 に入る前に、次の内容を一通り触っておくとスムーズです（合計3〜5時間程度）。

- 変数（`const` と `let`）、文字列と数値
- `if` 文と比較（`===`）
- 関数（`function` とアロー関数 `() => {}`）
- 配列とオブジェクトの基本
- `import` と `export`（ファイルを分けて関数を使う）

教材は [MDN の JavaScript ガイド](https://developer.mozilla.org/ja/docs/Web/JavaScript/Guide) の「文法とデータ型」「制御フローとエラー処理」「関数」あたりがおすすめです。
分からないところは Slack の #questions で聞くか、Claude に聞いてください。

## 9. 開発の始め方

はじめて clone したら、リポジトリのフォルダで次のコマンドを実行して、開発に使う道具をインストールします。

```
npm install
```

画面を見るときは、次のコマンドで開発用サーバーを起動します。

```
npm run dev
```

ターミナルに表示される URL（`http://localhost:5173/` など）をブラウザで開くと、画面が見られます。
止めるときは、ターミナルで `Ctrl + C` を押します。
